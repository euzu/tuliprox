# Code Review: tuliprox Backend — 2026-04-12

4 Subagents haben den gesamten Backend-Code analysiert (Performance, Deadlocks, Idiomacy, Duplication, Regressions). **Keine Deadlocks gefunden** — die Lock-Discipline ist exzellent. Die Hauptprobleme liegen bei Performance-Bottlenecks, Duplication und ein paar correctness-Risks.

---

## Critical / Important

### 1. Doppelte Provider-Connection-Release (Regression)
**File:** `backend/src/api/model/streams/provider_stream_factory.rs:739` und `:893`

`get_provider_stream` released die Provider-Connection bei Retry-Exhaustion, returned `Err`. `create_provider_stream` catched den `Err` und released **nochmal**. Double-decrement des `current_connections` Counters.

**Fix:** `release_provider_connection` nur an einer Stelle aufrufen.

---

### 2. Cleanup-Queue dropped Events stumm (Connection Leak)
**File:** `backend/src/api/model/connection_manager.rs:611-621`

Bei hoher Last wird die Cleanup-Queue (cap 4096) voll. `ReleaseStream`/`ReleaseConnection` Events gehen verloren. Phantom-Connections sammeln sich an — das System denkt irgendwann, alle Slots seien belegt.

**Fix:** Bei `Full` mit Timeout blockieren, oder Metrik + periodischen Reconciliation-Sweep einbauen.

---

### 3. Blocking I/O im Async-Context
| File | Line | Call |
|------|------|------|
| `processing/processor/playlist.rs` | 393 | `std::fs::create_dir_all` in `async fn` |
| `api/model/qos_aggregation_manager.rs` | 331, 412, 439 | `std::fs::read_dir`, `std::fs::metadata` in async task |

Blockiert Tokio-Worker-Threads. Bei vielen Verzeichnissen kann das den gesamten Runtime stalling.

**Fix:** `tokio::fs::create_dir_all` oder `spawn_blocking` um die ganzen Directory-Operationen.

---

### 4. `tee_dyn_reader` schluckt Read-Errors stumm
**File:** `backend/src/api/model/streams/persist_pipe_stream.rs:129`

```rust
Ok(0) | Err(_) => break,  // Error wird ignoriert
```

Wenn der Provider die Connection dropped, endet der Stream lautlos. Client weiß nicht ob sauberes EOF oder Fehler.

**Fix:** Vor dem `break` loggen + optional an den Consumer propagieren.

---

### 5. Kein Timeout beim Graceful Shutdown
**File:** `backend/src/api/main_api.rs:368`

`connection_manager.shutdown().await` kann unendlich hängen wenn z.B. ein Channel voll ist. Prozess terminiert bei SIGTERM nie.

**Fix:** `tokio::time::timeout(Duration::from_secs(30), ...)` drumherum.

---

### 6. Production `panic!()` / `unwrap()`
**File:** `backend/src/model/config/app.rs:450-454`

```rust
fn get_server_info(...) -> ApiProxyServerInfo {
    // ...
    server_info_list.first().unwrap().clone()  // panic! wenn Liste leer
}
```

Verletzt die Projekt-Konvention (keine `unwrap()`/`expect()`/`panic!()` in Production).

**Fix:** `Option<ApiProxyServerInfo>` returnen.

---

## Performance

### 7. Globaler Cache-Mutex serialisiert alle Resource-Requests
**File:** `backend/src/api/api_utils.rs:2102`

Jeder Image/Logo/EPG-Request acquires einen `tokio::sync::Mutex<LRUResourceCache>`. Reads blockieren gegeneinander.

**Fix:** `RwLock` oder `DashMap` — Cache-Hits sollten sich nicht gegenseitig blockieren.

---

### 8. LRU-Cache O(n) Scan bei jedem Hit
**File:** `backend/src/utils/lru_cache.rs:165`

`usage_order.iter().position()` ist linear. Bei Tausenden von Cache-Einträgen ein Bottleneck.

**Fix:** `LinkedHashMap` oder `HashMap<String, usize>`-Index für O(1) Position-Lookup.

---

### 9. `get_headers_from_request` allociert pro Request
**File:** `backend/src/api/api_utils.rs:1930-1938`

Jede Stream-Request erzeugt ein neues `HashMap<String, Vec<u8>>` mit `String` + `Vec<u8>` pro Header. Unter Last mit tausenden Streams signifikante Allocator-Pressure.

**Fix:** Small-Vec oder Array-Map für die wenigen tatsächlich benötigten Header.

---

### 10. `separate_number_and_remainder` allociert auf Hot-Path
**File:** `backend/src/api/api_utils.rs:2126-2134`

Könnte `(&str, Option<&str>)` oder `Cow<'_, str>` statt `(String, Option<String>)` returnen. Wird auf jedem Xtream-Stream-Request aufgerufen.

---

### 11. Adaptive Expiry hält zwei Locks gleichzeitig
**File:** `backend/src/api/model/active_user_manager.rs:1514-1515`

```rust
let mut expiry_index = self.adaptive_expiry_index.lock().await;
let mut user_connections = self.connections.write().await;
```

Beide Locks werden ~80 Zeilen lang gleichzeitig gehalten. Blockiert alle User-Connection-Operationen während der Verarbeitung.

**Fix:** Batches sammeln — `expiry_index` locken, due entries sammeln, releasen. Dann `connections` locken, Batch verarbeiten.

---

### 12. Burst Buffer `RwLock` — Writer starves Readers
**File:** `backend/src/api/model/streams/shared_stream_manager.rs:411-412`

Write-Lock auf jeden Chunk vom Provider. Neue Subscriber (Read-Lock) blockieren bis der Write-Lock released wird.

**Fix:** `Mutex` statt `RwLock` (writes frequent, reads infrequent) oder Lock-free Ring-Buffer.

---

### 13. B+Tree Backoff mit sub-ms Sleep
**File:** `backend/src/repository/bplustree.rs:3955-3975`

Initial backoff `Duration::from_micros(10)`. Linux-Timer-Granularität ist ~1ms — der µs-Sleep schläft trotzdem ~1ms.

**Fix:** Initial backoff auf 1ms erhöhen.

---

## Code Duplication (Hoch)

### 14. ~250 Zeilen duplizierte Stream-Handler-Logik
**Files:** `backend/src/api/endpoints/xtream_api.rs`, `m3u_api.rs`, `hls_api.rs`

Teilen fast identische Logik für:
- User Auth + Permission Check
- `resolve_admission_with_strategies` Block (3x kopiert, ~20 Zeilen pro Vorkommen)
- Session Lookup + Exhaustion Check (~50 Zeilen)
- `admission_failure_response` Pattern (8+ Vorkommen across Files)

**Fix:** Shared `resolve_stream_session()` Funktion extrahieren die Auth, Admission, Session Lookup übernimmt und ein `StreamSession` Struct returned. `check_user_permission()` Helper für das Permission-Check + Response Pattern.

---

### 15. `get_xtream_output` / `get_m3u_output` / `get_hdhomerun_output`
**File:** `backend/src/model/config/target.rs:230-254`

3 fast identische Methoden, jede mit `find()` + `matches!()` + `if let Some()`.

**Fix:** `find_map()` Pattern:
```rust
pub(crate) fn get_xtream_output(&self) -> Option<&XtreamTargetOutput> {
    self.output.iter().find_map(|o| match o {
        TargetOutput::Xtream(output) => Some(output),
        _ => None,
    })
}
```

---

### 16. `get_missing_vod_info_count` / `get_missing_series_info_count`
**File:** `backend/src/repository/playlist_source.rs:163-185`

Zwei Methoden, die sich nur im Feld (`vod` vs `series`) und Item-Typ unterscheiden.

**Fix:** Eine generische Methode mit Parametern.

### 20. Manual Count Loops statt `.filter().count()`
**File:** `backend/src/repository/playlist_source.rs:163-185`

```rust
// Current: manual loop + counter

for (_, item) in query.iter() {
    if item.item_type == PlaylistItemType::Video && item.provider_id > 0 && !item.has_details() {
        count += 1;
    }

// Idiomatic:
q.iter().filter(|(_, item)| {
    item.item_type == PlaylistItemType::Video && item.provider_id > 0 && !item.has_details()
}).count()
```

## Deadlocks: Keine gefunden

Die Lock-Discipline ist durchgehend exzellent:

- DashMap-Werte werden immer **rausgeklont** bevor ein `.await` auf dem inneren Lock (`provider_lineup_manager.rs:666-694`)
- `parking_lot::Mutex` wird nie über `.await` gehalten (`metadata_update_manager.rs:627,853`)
- Channel-Sender nutzen `try_send()` (non-blocking) — verhindert Backpressure-Deadlocks
- Lock-Reihenfolge ist konsistent über alle Code-Pfade
- `gc()` nutzt `try_write()` mit CAS-Rollback statt blockierendem Lock
- Explizite Kommentare dokumentieren Lock-Ordering-Entscheidungen
