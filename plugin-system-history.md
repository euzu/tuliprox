# Tuliprox Plugin System — Revision History & Verification Log

> Companion to [`plugin-system-plan.md`](plugin-system-plan.md) (design) and [`plugin-system-phases.md`](plugin-system-phases.md) (phases). It
> records *why* the design looks the way it does and which code facts each
> correction rests on. When re-verifying (§19.4), diff against the tables here.

> **Revision 4.3 (2026-10-31) — repository marketplace roadmap.**
>
> - Keep the initial plugin release repository-free; add manual marketplace
>   browsing/install after Phase 8, then boot updates in a separate phase.
> - A repository is configured by the direct HTTPS/raw URL to its root
>   `marketplace.json`. The catalog has release metadata and HTTPS package URLs,
>   but no publisher checksum, signature, or trusted-key configuration. The
>   admin trusts configured sources; Tuliprox calculates its own installed hash
>   for the existing approval pin.
> - Boot updates default off, do not auto-install or enable plugins, require
>   approval for capability changes, and retain rollback to the prior package.
>
> **Revision 4.2 (2026-10-30) — features added.**
>
> - **Scheduled plugin tasks** (§7, §5 `tasks` interface + `task-plugin` world,
>   manifest `tasks:`, Phase 4 item 8). Tasks ride the existing scheduler as a
>   unit `ScheduleTaskType::PluginTask` (the enum is `Copy`) and reuse
>   `ScheduledTaskFailed` for failures.
> - **Plugin functions as MCP tools** (§7, Phase 6 item 3a). There is a dynamic
>   tool source beside the static `MCP_TOOLS`, behind three default-off
>   switches, with forced redaction, and write tools are hidden in read-only
>   mode.
> - Gap fixed: `rpc_exports` had no WIT export. Added `interface rpc` +
>   `rpc-plugin` world, and typed `rpc_exports` entries (kind, schema, mcp flag).
>
> **Revision 4.1 (2026-10-30) — design fixes and additions, no new code facts.**
>
> - **Defect: WIT world.** A single `world plugin` exporting ten interfaces
>   forced every author to implement all ten. It is now one world per capability
>   over a shared `base`, with host-side export discovery (§5).
> - **Defect: UI trust.** In-page custom elements could read the admin token
>   (it is stored in `LocalStorage`). Plugin UI now runs only in
>   `sandbox="allow-scripts"` iframes with an opaque origin,
>   `connect-src 'none'` and a parent-validated `postMessage` bridge (§9, §11).
> - **Defect: sync/async.** Most hook sites are synchronous fns, and plugin
>   calls are async. Added a no-`block_on` rule and three bridging patterns
>   (lifted loop, prepare → apply, blocking-thread bridge). The two hooks that
>   need the bridge (EPG conflict, mapper plugin calls) are moved to v1.x (§7).
> - Added: **Phase S walking skeleton** before 0A/0/1 (§16, §19.3); **plugin
>   fingerprint, determinism contract and watch attribution** (§7); a
>   **global memory budget, per-plugin instance cap and pooling** (§7);
>   **`wasi:http`** replacing the custom `http-fetch` (§5, §8); **plugin
>   secrets** handling (§9, §11).
> - The document was split into design / phases / history files (this file is the
>   history).
>
> **Revision 4.** Re-verified against `develop` at v3.3.170 (`a8653d09`,
> 2026-10-30), 173 commits after revision 2. Still nothing plugin-specific is
> implemented. The ground moved substantially: `playlist.rs` is now a
> `playlist/` module, stage hooks can no longer take a `&mut PlaylistSource`,
> dedup is two passes on either side of a new **curation** stage, the two
> event "gaps" Phase 4 was going to close are already on the bus (43 event
> kinds, `u64` mask), Phase 0A largely duplicates the existing
> `core::utils::network::request` stack, and one release target (armv7)
> has no Cranelift backend. §2.6 lists every delta and where it was applied;
> §19 adds an execution strategy for running the phases with parallel agents
> on tiered models. Line anchors below were read from the code on 2026-10-30
> and will drift — §19.4 makes re-anchoring a cheap per-phase step.
>
> **Revision 3 preparation note.** The plugin-free processing foundations are now
> implemented: explicit filter/rename/map stages, counted filter and mapper
> outcomes, optional mapper rule names, immutable `Arc` mapping snapshots with
> indexed lookup, host-applied sort permutations, explicit finalization order,
> and bounded mapping diagnostics. No plugin runtime, configuration, WIT, or
> hooks have been added.
>
> **Revision 2.** Re-verified against the workspace on 2026-08-27, after the
> modularization and static-dispatch work landed (46 commits on
> `static-dispatch-refactor`). Revision 1 was written against a three-crate
> workspace and addresses everything as `backend/src/…`; the backend is now
> **18 crates**, the processing pipeline is **generic over a static `EventSink`
> bound** rather than threading an `Option<Arc<EventManager>>`, the event bus
> grew a filtered subscription seam built explicitly *for* this plan, and
> several things revision 1 proposed to build **already exist**. One revision-1
> claim was simply wrong (stream lifecycle events are already on the bus) and
> one example plugin is now a built-in feature.
>
> §2.5 is the full delta with its consequences; the affected sections are
> updated in place. Nothing here is implemented yet — no `plugins` crate, no
> `PluginsConfig`, no manifest parsing. The plan is still a proposal; what
> changed is the ground it stands on.
